# FitMate AI

FitMate AI 是一个 AI 健身聊天助手原型。项目目标是通过自然语言交互理解用户的健身目标、身体状态、训练限制、训练偏好和可用时间，并据此生成、调整和执行个性化训练计划。

当前项目采用 Next.js App Router 构建，前端体验、API Route、服务端 AI 编排、领域规则和共享类型已经按目录做了初步分层。现阶段仍以本地原型和静态动作数据为主，后续会逐步接入数据库、鉴权、用户画像、计划持久化和完整的 AI Tool Calling 闭环。

更完整的架构说明见 [docs/architecture.md](./docs/architecture.md)。

## 当前状态

当前项目主要完成了以下原型能力：

- 首页 AI 聊天界面，支持 DeepSeek 流式响应。
- 聊天页可识别训练计划生成意图，并在服务端生成经过候选动作与规则校验的训练计划草稿。
- 动作库页面，基于 `data/exercises.zh.json` 展示、搜索、筛选动作。
- 动作编排页面，支持从动作库添加动作、调整组数/次数/休息、保存到本地。
- 训练日历页面，支持本地安排训练、设置休息日、标记完成/未完成。
- 训练执行页面，支持倒计时、动作切换、暂停、结束训练。
- 基础响应式 UI、Tailwind CSS 主题和侧边栏导航。
- 前端页面与服务端业务代码已分离：`features/` 承载前端功能模块，`lib/server/` 承载服务端服务，`lib/shared/` 承载共享类型和 Schema。

注意：当前仍是前端原型 + 静态动作数据 + 服务端 AI 编排的阶段，尚未接入数据库、鉴权、服务端训练计划持久化或 AI 工具调用闭环。

## 对话流程说明

FitMate AI 的对话流程不是简单地把用户输入转发给大模型，而是把自然语言聊天拆成“理解意图、补全信息、生成草稿、服务端校验、用户确认、保存执行”的分层流程。这样做的目的是让 AI 负责擅长的理解和生成，让后端负责确定性的规则、安全边界和最终执行，避免模型直接产出不可控的训练计划。

用户进入首页后，首先通过聊天描述自己的训练目标、经验水平、每周可训练频率、单次可用时间、可用器械、伤病限制和动作偏好。前端负责收集对话上下文、展示流式回复，并在识别到用户有生成训练计划的意图时，请求服务端计划生成接口，而不是在浏览器里直接拼接业务逻辑或调用模型。

服务端收到计划生成请求后，会先把聊天上下文整理成可执行的用户训练意图。这个步骤的价值在于把自由文本转化为结构化输入，让后续动作筛选、风险控制和计划校验都有明确依据。对于健身场景来说，训练目标、经验、疼痛或伤病、器械条件和可用时间都会直接影响计划安全性，所以这些信息不能只停留在聊天文本里。

在生成计划前，系统会基于用户意图从动作库中筛选候选动作，并应用基础安全规则。例如，新手优先使用低风险动作；存在疼痛或伤病描述时，过滤高冲击或高风险动作；训练器械受限时，只保留用户实际可完成的动作。这样做是为了让模型只能在受控候选范围内组合计划，降低生成不存在动作、危险动作或不符合条件动作的概率。

AI 编排层随后基于用户意图和候选动作生成训练计划草稿。模型输出不会被直接保存或执行，而是必须返回符合结构约束的数据，包括计划标题、目标、周频率、训练日、动作、组数、次数或时长、休息时间和安全提示。选择结构化输出是为了把自然语言生成结果变成后端可验证、前端可展示、后续可持久化的数据结构。

计划草稿生成后，服务端会再次执行校验。校验内容包括动作 ID 是否存在、动作是否来自候选集、训练时长是否合理、组数和次数是否落在可接受范围内、休息时间是否异常，以及是否包含不适合用户条件的安排。这个步骤是系统的安全闸门：AI 可以提出方案，但只有通过规则校验的方案才会进入产品流程。

通过校验后，前端会把计划以卡片形式展示给用户，包括每个训练日的安排、动作明细和安全提示。用户可以在聊天中继续要求调整，例如缩短时长、替换动作、降低强度或避开某类动作。这样设计是为了保留自然语言交互的灵活性，同时让每次调整仍然回到服务端生成和校验流程中，而不是只在前端临时修改显示内容。

当用户确认计划后，当前原型会把计划草稿转换为训练编排模块使用的数据结构，并保存到本地训练历史中。后续接入 PostgreSQL、Prisma、用户鉴权和服务端持久化后，确认后的计划会进入数据库，成为训练日历、训练执行、反馈收集和长期个性化调整的事实数据来源。

整体流程可以概括为：

```txt
用户自然语言输入
  ↓
前端聊天状态与意图触发
  ↓
服务端整理用户训练意图
  ↓
动作候选筛选与安全过滤
  ↓
AI 生成结构化训练计划草稿
  ↓
服务端规则校验和动作 ID 校验
  ↓
前端展示计划并支持继续对话调整
  ↓
用户确认保存
  ↓
训练编排、日历和执行流程复用该计划
```

这个流程体现了项目的核心架构取舍：聊天体验在前端，HTTP 边界在 API Route，AI 生成在编排层，健身规则在领域服务层，动作数据和未来用户数据由数据层提供。各层职责清晰后，系统后续可以平滑扩展到数据库持久化、用户画像、Tool Calling、向量检索、训练反馈和自动调计划，而不需要把所有逻辑堆进聊天组件或单个 API 接口中。

## 本地运行

安装依赖：

```bash
npm install
```

配置环境变量：

```bash
cp .env.example .env.local
```

在 `.env.local` 中填写：

```bash
DEEPSEEK_API_KEY=
```

启动开发服务：

```bash
npm run dev
```

常用检查命令：

```bash
npm run typecheck
npm run lint
npm run build
```

## 目录说明

项目按 Next.js App Router 和前后端边界进行组织：

```txt
app/
  api/                     # Route Handlers，仅做 HTTP 入参/出参和服务层调用
    ai/workout-plan/       # AI 训练计划草稿生成接口
    chat/                  # 聊天流式响应接口
    exercises/             # 动作库查询接口
  page.tsx                 # 首页路由入口，渲染聊天功能模块
  composer/page.tsx        # 动作编排页路由入口
  exercises/page.tsx       # 动作库页路由入口
  plans/page.tsx           # 训练计划页路由入口
  training/page.tsx        # 训练执行页路由入口

components/
  app/                     # 跨功能复用的应用级 UI，如侧边栏、Logo、图标

features/
  chat/                    # 前端聊天功能模块
    api/                   # 浏览器侧 API client
    components/            # 聊天页面 UI
    hooks/                 # 聊天状态机和流式读取逻辑
    lib/                   # 聊天历史、计划触发解析等前端工具
    types.ts               # 聊天相关类型
  exercises/               # 前端动作库功能模块
  workouts/                # 前端训练编排、计划、执行相关页面组件
  workout-plans/           # 前端训练计划转换与保存相关工具

lib/
  client/                  # 浏览器专用基础设施
    http/client-request.ts # 前端统一请求函数
  server/                  # 服务端专用基础设施和业务服务
    http/server-request.ts # 服务端外部 HTTP 请求函数
    exercises/             # 服务端动作库查询服务
    workout-plans/         # AI 计划生成、候选动作、计划校验服务
  shared/                  # 前后端共享类型、Schema 和纯数据结构
    exercises/
    workout-plans/

data/
  exercises.zh.json        # 当前使用的中文动作静态数据

scripts/                   # 动作数据清洗、翻译和修正脚本
tests/                     # 当前项目内的逻辑测试脚本
docs/                      # 架构与设计文档
example/                   # 设计参考 HTML
```

分层约定：

- `app/api/*` 不直接堆业务逻辑，复杂流程下沉到 `lib/server/*`。
- `features/*` 是前端功能模块，可以引用 `lib/client/*` 和 `lib/shared/*`，不应引用 `lib/server/*`。
- `lib/server/*` 是服务端专用代码，可以引用 `lib/shared/*`，不应引用 `lib/client/*`。
- `lib/shared/*` 只放前后端都可安全使用的类型、Schema 和纯函数，不放数据库、环境变量、外部 API 密钥或浏览器状态。
- `components/app/*` 只放跨功能复用的应用级 UI，页面级组件优先放在对应 `features/*/components` 中。
