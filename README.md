# FitMate AI

FitMate AI 是一个 AI 健身聊天助手原型。项目目标是通过自然语言交互理解用户的健身目标、身体状态、训练限制、训练偏好和可用时间，并据此生成、调整和执行个性化训练计划。

当前项目采用 Next.js App Router 构建，前端体验、API Route、服务端 AI 编排、领域规则和共享类型已经按目录做了初步分层。现阶段仍以本地原型和静态动作数据为主，后续会逐步接入数据库、鉴权、用户画像、计划持久化和完整的 AI Tool Calling 闭环。

更完整的架构说明见 [docs/architecture.md](./docs/architecture.md)。

## 当前状态

当前项目主要完成了以下原型能力：

- 首页 AI 聊天界面，支持 DeepSeek 流式响应。
- 聊天页可识别训练计划生成意图，并在服务端生成经过候选动作与规则校验的训练计划草稿。
- 动作库页面，基于 `data/exercises.zh.json` 展示、搜索、筛选动作。
- 动作编排页面，支持从动作库添加动作、调整组数/次数/休息、保存到本地。
- 训练日历页面，支持本地安排训练、设置休息日、标记完成/未完成。
- 训练执行页面，支持倒计时、动作切换、暂停、结束训练。
- 基础响应式 UI、Tailwind CSS 主题和侧边栏导航。
- 前端页面与服务端业务代码已分离：`features/` 承载前端功能模块，`lib/server/` 承载服务端服务，`lib/shared/` 承载共享类型和 Schema。

注意：当前仍是前端原型 + 静态动作数据 + 服务端 AI 编排的阶段，尚未接入数据库、鉴权、服务端训练计划持久化或 AI 工具调用闭环。

## 对话流程说明

对话流程用于展示用户从自然语言输入到获得可执行训练建议的完整链路。每一步都分成“做了什么”和“为什么这么做”，便于说明系统不是单纯聊天，而是把 AI 能力、业务规则和训练数据串成一个可控流程。

### 1. 接收用户输入

- 做了什么：用户在聊天框中输入目标、身体情况、训练经验、器械条件、训练时间等自然语言信息。
- 为什么这么做：健身需求通常不是固定表单能一次收集完整的，用聊天方式可以降低输入成本，也更适合表达伤病、偏好和临时限制。

### 2. 调用大模型接口分析意图

- 做了什么：系统将当前用户输入和历史对话发送给大模型，判断用户是在咨询单次训练建议、生成周期训练计划、修改已有计划，还是普通健身问答。
- 为什么这么做：不同意图对应不同后续流程。单次推荐更关注今天怎么练，计划推荐更关注每周频率、训练拆分和长期安排，先判断意图可以避免所有请求都走同一套重流程。

### 3. 判断信息是否足够

- 做了什么：系统检查生成建议所需的关键信息是否完整，例如训练目标、经验水平、每次可用时间、每周训练频率、器械、伤病或疼痛限制。
- 为什么这么做：信息不足时直接生成计划容易不准确，也可能忽略安全风险。先判断缺失项，可以让 AI 继续追问，而不是过早给出不可靠方案。

### 4. 确认推荐类型

- 做了什么：当用户需求明确后，系统区分是“单次训练推荐”还是“周期训练计划推荐”。单次推荐生成一节训练内容，周期计划生成一周或多周的训练安排。
- 为什么这么做：两类结果的数据结构和校验规则不同。单次推荐重点是动作、组数、次数、休息和预计时长；周期计划还需要考虑训练日分布、肌群安排、恢复时间和整体强度。

### 5. 整理用户训练意图

- 做了什么：服务端把自然语言对话整理成结构化训练意图，包括目标、经验、训练频率、单次时长、器械、偏好动作、避开动作和风险限制。
- 为什么这么做：后续动作筛选、计划生成和规则校验都需要明确字段。将文本转成结构化数据后，系统可以稳定地执行过滤、校验和展示。

### 6. 查询并筛选候选动作

- 做了什么：系统根据训练意图从动作库中筛选候选动作，只保留符合目标、部位、难度、器械和风险要求的动作。
- 为什么这么做：AI 不应该凭空编造动作，也不应该推荐用户无法完成或不适合的动作。先给出候选范围，可以让模型在受控动作库内生成内容。

### 7. 应用安全规则

- 做了什么：系统对候选动作和计划要求应用安全过滤，例如新手优先低风险动作，有疼痛或伤病描述时排除高冲击动作，器械不足时排除不可执行动作。
- 为什么这么做：健身建议存在安全边界。让确定性的后端规则先介入，可以降低模型忽略风险条件的概率。

### 8. 生成训练建议草稿

- 做了什么：系统调用大模型，基于用户训练意图和候选动作生成结构化训练建议草稿。草稿包含标题、训练目标、动作列表、组数、次数或时长、休息时间和注意事项。
- 为什么这么做：大模型适合把结构化条件组合成符合用户需求的训练方案，但输出必须是结构化数据，方便后端校验和前端展示。

### 9. 服务端校验 AI 输出

- 做了什么：服务端校验 AI 返回结果，包括动作 ID 是否存在、是否来自候选动作、组数次数是否合理、训练时长是否异常、是否违反伤病或器械限制。
- 为什么这么做：AI 生成结果不能直接保存或执行。服务端校验是最终安全闸门，确保只有符合规则的数据进入产品流程。

### 10. 前端展示结果

- 做了什么：前端把通过校验的训练建议展示为可读卡片，包括训练日、动作、强度、休息和安全提示。
- 为什么这么做：用户需要看到结构清晰的训练内容，并能理解每一步要做什么，而不是只收到一段难以执行的自然语言回复。

### 11. 支持继续对话调整

- 做了什么：用户可以继续提出修改要求，例如缩短时间、降低强度、替换动作、避开某个部位或改成居家训练。
- 为什么这么做：训练计划通常需要多轮确认。继续使用对话调整，可以保留自然语言交互体验，同时每次调整仍然回到服务端生成和校验流程。

### 12. 用户确认并保存

- 做了什么：用户确认后，系统将训练建议转换为训练编排模块可使用的数据结构，并保存到当前本地训练历史中。
- 为什么这么做：聊天生成的内容需要进入后续训练流程，才能被训练日历、训练执行和训练记录复用。当前原型先使用本地保存，后续会迁移到服务端数据库。

整体流程：

```txt
用户自然语言输入
  ↓
调用大模型接口分析意图
  ↓
判断信息是否足够
  ↓
确认单次推荐或计划推荐
  ↓
整理结构化训练意图
  ↓
查询动作库并筛选候选动作
  ↓
应用安全规则
  ↓
生成结构化训练建议草稿
  ↓
服务端校验 AI 输出
  ↓
前端展示结果
  ↓
用户继续调整或确认保存
```

## 技术栈

- Next.js App Router
- React
- TypeScript
- Tailwind CSS
- DeepSeek Chat Completions API

## 本地运行

安装依赖：

```bash
npm install
```

配置环境变量：

```bash
cp .env.example .env.local
```

在 `.env.local` 中填写：

```bash
DEEPSEEK_API_KEY=
```

启动开发服务：

```bash
npm run dev
```

常用检查命令：

```bash
npm run typecheck
npm run lint
npm run build
```

## 目录说明

项目按 Next.js App Router 和前后端边界进行组织：

```txt
app/
  api/                     # Route Handlers，仅做 HTTP 入参/出参和服务层调用
    ai/workout-plan/       # AI 训练计划草稿生成接口
    chat/                  # 聊天流式响应接口
    exercises/             # 动作库查询接口
  page.tsx                 # 首页路由入口，渲染聊天功能模块
  composer/page.tsx        # 动作编排页路由入口
  exercises/page.tsx       # 动作库页路由入口
  plans/page.tsx           # 训练计划页路由入口
  training/page.tsx        # 训练执行页路由入口

components/
  app/                     # 跨功能复用的应用级 UI，如侧边栏、Logo、图标

features/
  chat/                    # 前端聊天功能模块
    api/                   # 浏览器侧 API client
    components/            # 聊天页面 UI
    hooks/                 # 聊天状态机和流式读取逻辑
    lib/                   # 聊天历史、计划触发解析等前端工具
    types.ts               # 聊天相关类型
  exercises/               # 前端动作库功能模块
  workouts/                # 前端训练编排、计划、执行相关页面组件
  workout-plans/           # 前端训练计划转换与保存相关工具

lib/
  client/                  # 浏览器专用基础设施
    http/client-request.ts # 前端统一请求函数
  server/                  # 服务端专用基础设施和业务服务
    http/server-request.ts # 服务端外部 HTTP 请求函数
    exercises/             # 服务端动作库查询服务
    workout-plans/         # AI 计划生成、候选动作、计划校验服务
  shared/                  # 前后端共享类型、Schema 和纯数据结构
    exercises/
    workout-plans/

data/
  exercises.zh.json        # 当前使用的中文动作静态数据

scripts/                   # 动作数据清洗、翻译和修正脚本
tests/                     # 当前项目内的逻辑测试脚本
docs/                      # 架构与设计文档
example/                   # 设计参考 HTML
```

分层约定：

- `app/api/*` 不直接堆业务逻辑，复杂流程下沉到 `lib/server/*`。
- `features/*` 是前端功能模块，可以引用 `lib/client/*` 和 `lib/shared/*`，不应引用 `lib/server/*`。
- `lib/server/*` 是服务端专用代码，可以引用 `lib/shared/*`，不应引用 `lib/client/*`。
- `lib/shared/*` 只放前后端都可安全使用的类型、Schema 和纯函数，不放数据库、环境变量、外部 API 密钥或浏览器状态。
- `components/app/*` 只放跨功能复用的应用级 UI，页面级组件优先放在对应 `features/*/components` 中。
