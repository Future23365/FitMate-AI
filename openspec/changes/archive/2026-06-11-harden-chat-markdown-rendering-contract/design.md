## 设计方向

本 change 把问题抽象为“用户可见聊天正文 Markdown 子集”合同，而不是针对 `8~12` 或某条 trace 增加特例。

设计分两层：

- 模型可见合同：告诉模型只使用适合聊天气泡的 Markdown 子集，避免会改变渲染结构或造成误解的语法。
- 前端渲染兜底：即使模型违反软约束，聊天正文也不应因为 GFM 解析规则显示删除线、水平线、表格、脚注、任务清单或 raw HTML。

## Markdown 子集

允许：

- emoji 和普通 Unicode 文本。
- 段落、短标题、编号列表、项目列表。
- 加粗、斜体、行内代码。
- 换行和空行。

禁止或降级：

- 删除线：`~text~`、`~~text~~`。
- 水平分割线：`---`、`***`、`___`、`<hr>`。
- raw HTML：例如 `<div>`、`<span>`、`<br>`、`<hr>`。
- Markdown 表格。
- 脚注。
- 任务清单：`- [ ]`、`- [x]`。
- 代码块。
- 一级大标题。

数字范围规则：

- 模型可见说明要求使用 `8-12`、`8 到 12` 或 `8 至 12`。
- 前端关闭 `remark-gfm` 的 `singleTilde`，避免历史或偶发输出里的 `8~12` 被解析成删除线。

## 抽象层级门禁

结论：可继续。

1. 抽象问题类型：用户可见 Markdown 渲染合同不足。
2. 通用合同修复：定义聊天正文 Markdown 子集，不使用具体用户短句作为触发条件。
3. 业务 tool 局部说明：本 change 不修改业务 tool。
4. 回归测试样例：使用健身训练区间和常见 Markdown 高风险结构作为格式测试样例。
5. 服务端语义分流检查：不新增关键词规则、自然语言模板路由、phrasing 特判或具体 toolName 语义分支。

## 取舍

- 不移除 `remark-gfm`：项目仍可保留 GFM 的常规列表和基础语法支持。
- 不让 response adapter 按用户语义改写正文：本次只做格式安全子集，不替模型判断业务含义。
- 不禁止 emoji：emoji 不改变结构，也符合用户可见表达需求。
- 不把所有 Markdown 都禁用：保留列表、加粗、短标题等对训练步骤说明有价值的结构。

## 验证

- OpenSpec strict validate。
- Prompt / final response schema 测试覆盖 Markdown 子集说明。
- 前端 Markdown 渲染测试覆盖 `8~12` 不生成删除线，以及水平线、HTML、表格、脚注、任务清单、代码块等结构不会按高风险结构渲染。
- TypeScript 检查。
