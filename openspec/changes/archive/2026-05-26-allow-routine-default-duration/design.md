## Context

聊天链路当前由意图解析模型输出 `canTriggerAction`，服务端再根据该字段派生 `assistant_action`。当用户已经给出明确动作列表并要求编成单次训练时，动作范围已经明确；如果只缺训练时长，继续追问会阻断后续 `workout_routine` 生成。

## Goals / Non-Goals

**Goals:**

- 明确动作列表 + 单次训练编排请求可以使用默认估算时长触发生成。
- 聊天正文需要说明当前使用了默认估算时长，并提示用户可以继续补充训练时长调整。
- 保持长期计划、宽泛训练请求和高风险健康场景的追问与安全边界。

**Non-Goals:**

- 不新增用户画像存储、读取或推断逻辑。
- 不改变 `assistant_action`、`suggested_replies`、训练计划生成接口或前端事件结构。
- 不改变数据库 Schema。

## Decisions

- 通过 Prompt 收窄 `canTriggerAction` 判定，而不是新增服务端硬编码兜底。原因是当前聊天触发策略已经以结构化意图解析为入口，继续由模型区分“明确动作列表”和“宽泛请求”能保持现有链路一致；后续若要更稳定，可再引入确定性解析。
- 默认估算仅适用于用户明确列出动作并要求编成单次训练的场景。原因是动作数量和动作类型已经提供了足够边界；“今天练什么”这类宽泛请求仍应继续追问目标、时长或场地。
- 可见回复只做自然提示，不列具体动作清单。原因是训练草稿仍由后续计划生成接口输出，聊天正文提前列清单会和结构化草稿冲突。

## Risks / Trade-offs

- [Risk] 只靠 Prompt 仍可能被模型偶发误判。→ Mitigation：增加针对 `resolveAssistantAction` 的单元测试，确保服务端在 `canTriggerAction=true` 时会稳定发出 `workout_routine`。
- [Risk] 默认时长可能不符合用户真实情况。→ Mitigation：可见回复明确说明使用默认估算，并提示用户可以补充时长调整；README 记录后续基于用户画像推测默认训练时长。
