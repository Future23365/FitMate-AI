## Context

RAG 混合检索现在已经能在服务端完成候选召回、硬过滤和排序。问题出在模型请求阶段：聊天模型、动作推荐模型和训练草稿模型仍收到偏宽的候选 payload，里面混有图片、英文名、长原因、重复候选池和 trace 级诊断信息。模型只需要知道“能选哪些动作、为什么大致适合、有哪些安全边界”，不需要完整动作展示数据。

## Goals / Non-Goals

**Goals:**
- 收敛发给模型的候选动作字段，降低短对话和自动卡片生成的 prompt token。
- 保留服务端完整动作对象，确保最终卡片、训练草稿落库、图片展示和校验不受影响。
- 让聊天回复、动作推荐和训练编排共用清晰的“模型候选摘要”思路。
- 用自动化测试覆盖不再向模型发送图片等非必要字段。

**Non-Goals:**
- 不改变 RAG/Hybrid Search 的召回、过滤和 rerank 算法。
- 不改变 API 响应结构、前端卡片展示字段或训练持久化结构。
- 不移除 trace 中用于调试的服务端诊断信息；只避免把诊断信息误当模型输入。

## Decisions

1. 模型 payload 只保留中文可理解字段和选择约束。

   保留 `exerciseId`、`nameZh`、`categoryZh`、`level`、`equipmentZh`、`primaryMusclesZh`、必要的 `secondaryMusclesZh`、`riskTags`、`goalTags`、`source` 或 `score`。删除 `imageUrl/imageUrls/images`、`nameEn`、`levelZh` 和完整 `candidateReasons`。原因是模型选择动作时中文名、器械、肌群、风险和标签足以表达语义，图片和英文名只服务 UI 或检索，不应进入生成上下文。

2. 动作推荐模型不再接收长原因。

   `candidateReasons` 通常包含 Hybrid Search 的全文匹配、向量分、业务加权等调试性文字，会显著增加 token。模型只需要候选本身和排序信号，推荐理由可由模型基于精简属性生成；服务端仍保留完整候选原因用于 trace。

3. 训练编排候选数量按任务收敛。

   当前训练草稿模型每个候选池最多 40 条，多个池子叠加后容易超过实际编排需要。将模型候选上限降低到能覆盖热身、主训练、拉伸和替代选择的范围，同时保留服务端完整候选池用于校验和兜底。

4. 测试关注模型请求边界。

   优先通过单元测试或路由测试验证构造出的模型请求不包含图片/英文名/长原因字段，并保留必要字段。这样比真实 LLM 测试更稳定，也符合当前变更不需要验证模型质量的范围。

## Risks / Trade-offs

- [Risk] 候选字段过少可能降低模型推荐理由的表达质量 → 保留肌群、器械、风险、目标标签、分类和分数，足够支撑短理由生成。
- [Risk] 训练编排候选数量减少后复杂计划的选择空间变窄 → 只降低模型输入上限，不改变服务端召回和校验；后续可按 trace 评估再细调。
- [Risk] trace 里仍展示完整候选对象会让人误以为模型也收到了这些字段 → 测试和命名明确区分 model payload 与 trace diagnostic payload。
