## Context

当前聊天链路已经具备服务端编排、数据库 grounding、动作候选筛选、结构化输出校验和 AI Trace 能力。随着整体 AI 架构完善，单轮请求可能同时运行意图解析、上下文总结、候选动作构建、动作/计划生成和最终自然语言回复，流程质量更稳，但 token 消耗也更高。

本次设计的核心约束是：不能退回自由发挥式 LLM 回复，也不能绕开动作库、结构化校验或服务端权限边界。优化方向应当是让每个 AI 阶段只在必要时运行，并且只接收当前阶段必要的上下文。

## Goals / Non-Goals

**Goals:**

- 建立服务端 AI token budget 决策层，统一决定本轮需要运行哪些 LLM 调用、上下文片段和 prompt module。
- 保留 `conversationSummary + latestUserMessage` 的上下文边界，避免重新引入完整历史消息窗口。
- 将候选动作 payload 瘦身为模型完成任务所需的字段白名单。
- 在 AI Trace 中按阶段展示 token 分账、跳过原因和上下文裁剪摘要，支持后续持续优化。
- 保持动作推荐、训练计划生成和最终回答的质量边界：动作必须来自数据库，模型输出必须经过服务端校验。

**Non-Goals:**

- 不引入真实 LLM 手测预算验收，不修改 `manual-llm-consistency-tests` 的测试命令、报告或 token 预算输出。
- 不更换模型供应商，不新增外部依赖。
- 不改变前端 `/api/chat` 的公开请求契约。
- 不把 token 优化做成用户可配置项；本阶段只做服务端策略和开发者可观测性。

## Decisions

### 1. 增加 AI token budget 决策层

在聊天服务端编排中新增一个预算决策对象，基于当前用户消息、已有 summary、解析后的意图、候选动作状态和动作触发条件，输出本轮需要运行的 AI 阶段、模型可见上下文、prompt modules 和跳过原因。

选择这个方案，是因为 token 成本来自多阶段组合，而不是某一个 prompt 文案。集中决策可以避免每个服务各自判断，减少重复传参和隐性成本。

备选方案是直接压缩现有 prompt。该方案改动更窄，但无法解决不必要 LLM 调用、候选字段过大和 trace 难分账的问题，因此不作为主方案。

### 2. Prompt module 化，而不是单一大 prompt

将模型指令按任务拆分为基础边界、意图解析、动作推荐、训练计划、单次训练、澄清问题和最终回答等模块。预算决策层只选择本轮需要的模块，避免每轮都携带所有业务规则。

选择这个方案，是因为不同意图需要的约束差异明显。动作推荐需要候选动作规则，普通健身解释不需要完整计划生成规则；澄清问题也不需要完整动作推荐输出协议。

### 3. 候选动作采用字段白名单

模型可见候选动作仅保留 `exerciseId`、中文名称、目标肌群、器械、难度、动作类型、匹配原因、必要限制和服务端评分摘要。完整数据库字段、长描述、内部 metadata、无关分类和重复标签继续留在服务端内部。

选择这个方案，是因为 grounding 的质量取决于候选动作是否正确，不取决于把完整数据库记录传给模型。字段白名单可以降低输入 token，同时让模型更专注于选择和解释。

### 4. Summary 更新从主回复质量路径中解耦

用户可见回复不应因为 summary 更新失败而失败。summary 更新仍作为后处理记录在 trace 中；当本轮没有新增长期事实时，预算决策层可以跳过 LLM summary 更新，使用现有 summary。

选择这个方案，是因为 summary 是下一轮上下文优化工具，不应该成为本轮回复稳定性的硬依赖。

### 5. Trace 记录分账和跳过原因

每个 AI 阶段都应记录阶段名称、是否执行、跳过原因、模型名称、prompt module、输入摘要、候选动作数量、token usage 和耗时。对于未执行阶段，trace 也要保留决策结果，方便确认“省 token”来自正确的 gating，而不是漏执行。

选择这个方案，是因为优化 token 必须可观测。只看总 token 无法判断问题发生在意图解析、候选上下文、summary 更新还是最终回答。

## Risks / Trade-offs

- [Risk] 预算决策层过于激进，导致应调用 LLM 的场景被跳过 → Mitigation：默认只跳过确定性场景；所有跳过路径必须写入 trace，并覆盖自动化测试。
- [Risk] 候选字段裁剪过度，导致模型缺少解释动作选择的依据 → Mitigation：字段白名单保留匹配原因、限制和服务端评分摘要；先从推荐链路最小必要字段开始。
- [Risk] Prompt module 拆分后规则分散，后续维护者难以判断完整约束 → Mitigation：集中维护模块注册表，并在预算决策 trace 中展示本轮启用的模块。
- [Risk] trace 字段增加导致开发期日志更大 → Mitigation：只记录摘要、计数、字段名和必要 token usage，不默认记录完整模型响应正文。
- [Risk] token 成本降低但质量回归不易察觉 → Mitigation：使用现有普通自动化测试、结构化校验测试和 trace fixture 校验关键质量边界；本 change 不要求真实 LLM 手测预算验收。

## Migration Plan

1. 先补预算决策层、prompt module 注册和候选字段白名单的纯函数测试。
2. 将 `/api/chat` 编排迁移为读取预算决策结果，再执行必要 AI 阶段。
3. 为动作推荐和训练计划生成接入瘦身后的候选动作模型输入。
4. 扩展 AI Trace 事件结构和 `/dev/ai-traces` 展示，使分账和跳过原因可见。
5. 运行相关自动化测试、类型检查和构建检查；不执行真实 LLM 手测预算验收。

## Open Questions

- 预算阈值是否需要配置化，还是先以内置常量落地。
- 候选动作 Top N 的默认数量是否按意图区分，例如动作推荐和长期计划生成采用不同上限。
- summary 更新跳过条件是否只基于结构化事实变化，还是同时参考用户消息长度和意图类型。
