## Context

`/training` 当前在主步骤倒计时 effect 中同时推进 `remainingSeconds` 和 `elapsedSeconds`。这个结构让总训练时长依赖当前步骤是否处于可推进状态：动作准备、暂停、无 active step 或步骤切换都会影响总时长。已有需求要求动作详情抽屉可以暂停训练流程，但本次需求明确要求“已训练”总时长只受用户手动暂停影响。

## Goals / Non-Goals

**Goals:**
- 为“已训练”建立独立计时逻辑，训练开始后单独累加总时长。
- 休息步骤、动作准备、步骤切换、语音提示等待和动作详情抽屉暂停训练流程时，总时长仍按训练已经开始的事实继续累计。
- 用户点击暂停时，同时暂停训练流程和总时长；用户点击继续后恢复二者。
- 保持现有步骤倒计时、计次、准备倒计时、语音播报和动作详情抽屉行为。

**Non-Goals:**
- 不修改训练时间线生成规则。
- 不修改计划持久化、完成状态或 API。
- 不新增浏览器端持久化恢复总时长。

## Decisions

### 拆分流程暂停和总时长暂停

保留 `isPaused` 作为训练流程暂停状态，用于步骤倒计时、准备倒计时和语音播报。新增只由用户暂停按钮控制的总时长暂停状态，使“已训练”不再被详情抽屉等非手动暂停状态影响。

取舍：也可以把所有暂停来源编码进一个枚举，但当前页面只需要区分“流程暂停”和“用户手动暂停总时长”，独立布尔状态更直接，改动范围更可控。

### 总时长使用独立 effect

新增独立 `useEffect` 负责 `elapsedSeconds` 累加，条件只依赖训练是否开始、计划是否可用、以及用户是否手动暂停。步骤倒计时 effect 只负责当前步骤剩余时间和自动推进。

取舍：没有引入自定义 hook，是因为计时状态目前只在训练页面内部使用；如果后续需要恢复、后台计时或多页面共享，再提取 hook 更合适。

## Risks / Trade-offs

- [Risk] 自动打开动作详情会暂停训练流程但不暂停总时长，用户可能看到步骤停住而总时长继续走。
  → Mitigation: 这是本次需求的直接语义，总时长表示开始训练后的累计时长，只有手动暂停影响。
- [Risk] 最后一项自动完成后如果 `hasStarted` 变为 false，总时长会停止。
  → Mitigation: 训练结束不属于“训练状态影响计时”的运行中场景；结束后停止计时符合完成态。
