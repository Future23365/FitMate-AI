## Context

`/training` 当前在计划加载后立即设置第一个步骤的 `preparationCountdown`，`isPaused` 初始为 `false`，相关 effect 会自动推进准备倒计时、训练计时和步骤切换。语音偏好如果从 `localStorage` 恢复为开启，语音状态会进入 `needs-activation`，页面再通过全局 `pointerdown` / `keydown` 监听把下一次训练页面手势当作恢复语音动作。

这个模型导致两个问题：

- 进入页面即开始训练，用户还没准备好就开始倒计时和自动推进。
- 暂停、跳步、列表点击等训练控制会被复用成语音恢复入口，用户会在不相关操作上看到“需要点击一次恢复语音”的提示。

新的设计把“训练开始”作为第一等状态，由显式开始按钮承载第一次用户手势。语音恢复不再绑定任意训练控制，而是在开始按钮或语音按钮中明确发生。

## Goals / Non-Goals

**Goals:**

- 进入 `/training` 后默认处于待开始状态，不运行准备倒计时、训练计时、计次、beep 或自动推进。
- 新增开始按钮，点击后才进入训练流程。
- 如果语音偏好已开启，开始按钮点击流中尝试激活语音并播报当前步骤。
- 移除“刷新后需要点击一次恢复播报”等恢复提示和任意训练控制自动激活逻辑。
- 暂停、继续、上一个、下一个、跳过休息只负责训练控制，不再承担语音权限恢复职责。

**Non-Goals:**

- 不改变训练 timeline 生成、动作选择、训练计划持久化或 API 契约。
- 不新增用户可编辑的语音规则 UI。
- 不引入服务端 TTS、AI 音频、麦克风或语音识别。
- 不改变语音配置文件的模板结构，除非为移除恢复提示所必需。

## Decisions

### 1. 使用显式 `hasStarted` 状态控制训练推进

`WorkoutSessionPage` 新增 `hasStarted` 状态。计划加载、手动切换计划或完成训练重置时，`hasStarted=false`。所有会推动训练时间的 effect 都必须同时满足 `hasStarted=true`：

- 准备倒计时 effect
- 主计时 effect
- 计次计算对应的语音播报 effect
- duration step 的 beep effect

这样训练是否运行不再依赖 `isPaused` 的初始值。`isPaused` 只表示已经开始后的暂停状态。

备选方案是把 `isPaused` 初始设为 `true` 并复用继续按钮作为开始按钮。这个方案改动少，但语义仍然混淆：暂停态和未开始态不是同一件事，且会继续触发暂停相关语音取消逻辑。

### 2. 开始按钮负责第一次训练手势和语音激活

新增 `handleStartTraining()`：

- 设置 `hasStarted=true`
- 设置 `isPaused=false`
- 如果语音支持且本地语音偏好开启，则调用 `voiceSession.activateCurrentStep()`
- 不展示恢复语音提示，不把开始动作命名为“恢复”

如果语音偏好已开启但页面还没有音频权限，开始按钮只做静默音频解锁并直接播报当前动作准备提示，不额外播报“语音播报已开启”。如果语音偏好关闭，开始按钮只启动训练；用户仍可点击语音按钮开启语音，只有这个开关动作才播报“语音播报已开启”。

语音调度器必须只在浏览器触发真实 speech 生命周期事件后才把 Web Speech 视为已启动。若 `speechSynthesis.speak()` 调用后在配置的启动等待时间内没有触发 `onstart` 或 `onend`，调度器将其标记为 `speech_blocked`，避免页面误认为语音成功并继续只播放 Web Audio beep。首次 voices 列表为空时，调度器会等待 `voiceschanged` 或配置的短超时后再创建 utterance。

### 3. 移除任意页面手势恢复语音

删除或停用 `shouldRetryVoiceActivation` 驱动的全局 `pointerdown` / `keydown` 监听。语音激活入口收敛为：

- 顶部语音按钮开启或重试
- 待开始状态的开始按钮

原因是浏览器播放权限确实需要用户手势，但这个手势应该是产品语义明确的动作，而不是暂停、跳步等任意控制。

### 4. 待开始状态不显示恢复语音浮层

保留首次访问语音提示，用于告诉用户顶部按钮可以开启动作播报。移除 `needs-activation` 导致的“刷新后需要点击一次恢复播报”浮层。语音按钮仍可通过图标状态表达开启/关闭/失败，失败时可以重试，但不在训练主区域制造额外恢复流程。待开始状态不渲染额外的大播放图标，主开始入口保留在底部训练控制中。

### 5. 手动跳步保持步骤可见，但不自动开跑

未开始时用户可以查看动作、打开详情或选择列表项。若未开始时切换步骤，页面更新当前步骤和剩余时间，但仍保持 `hasStarted=false`，不启动倒计时。点击开始后从当前选中的步骤开始。

已开始后，现有上一个、下一个、跳过休息和列表选择行为保持原有自动推进语义。

## Risks / Trade-offs

- [Risk] 训练页上的“暂停/继续”与新增“开始”按钮同时存在可能造成状态混乱。→ Mitigation: `hasStarted=false` 时主控制显示“开始”，不显示或禁用暂停语义；开始后才显示暂停/继续。
- [Risk] 语音偏好已开启但浏览器仍阻止 speech 时，用户可能只听到 beep。→ Mitigation: 开始按钮内先尝试 speech 激活；语音状态失败只影响语音，不阻塞训练。
- [Risk] 旧的恢复提示测试和 spec 与新行为冲突。→ Mitigation: 更新 voice broadcast spec，把恢复入口收敛到开始按钮和语音按钮，并删除任意训练控制恢复语音要求。
- [Risk] 计划加载期间状态重置不完整会导致旧计时器继续运行。→ Mitigation: 加载计划时统一重置 `hasStarted=false`、`isPaused=false`、准备 key、倒计时和剩余时间。

## Migration Plan

1. 更新 OpenSpec delta，明确训练页待开始状态和语音激活入口。
2. 在训练页新增 `hasStarted` 状态和 `handleStartTraining()`。
3. 用 `hasStarted` 保护准备倒计时、主计时和语音事件 effect。
4. 修改训练控制 UI，未开始时展示“开始”，开始后展示暂停/继续。
5. 移除任意手势恢复语音监听和恢复语音浮层文案。
6. 补充测试并运行相关自动化检查。

回滚策略：如果开始态接入引发训练推进回归，可以保留 `hasStarted` 状态但临时恢复旧的自动开始逻辑；语音恢复提示不应恢复为任意控制触发。

## Open Questions
