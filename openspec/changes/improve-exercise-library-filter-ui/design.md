## Context

动作库页面已经支持 `category`、`level`、`force`、`mechanic`、`equipment`、`muscle`、`goalTag`、`riskTag`、`homeRequirement`、`published`、`sort`、`pageSize` 等查询能力，并通过 facets 返回可用选项。当前问题集中在 UI 信息架构：所有筛选几乎都是下拉框，肌群单独外露但和下方筛选割裂，排序和每页数量也混在筛选流中。

## Goals / Non-Goals

**Goals:**

- 让动作库默认首屏优先展示动作列表，避免筛选区占据过多纵向空间。
- 让高频筛选维度保持快速可点，但从默认页面主体迁移到筛选抽屉中。
- 让低频筛选保持可访问，但不占据主要视觉空间。
- 让已选筛选条件可见、可单项移除、可一次清空。
- 将排序和每页数量放到结果工具栏，避免和筛选语义混淆。
- 保持现有 API 查询参数和数据加载逻辑不变。

**Non-Goals:**

- 不新增筛选维度或修改筛选算法。
- 不调整 `/api/exercises` 契约、分页语义或 facets 数据结构。
- 不改动作详情面板、动作卡片内容或训练编排页右侧动作库。

## Decisions

- 默认页面使用 sticky 搜索工具栏，只保留搜索框、筛选入口、已选数量和已选条件横向 chips。相比四条筛选行常驻页面，这能把首屏纵向空间还给动作列表。
- 核心筛选使用统一 `ChipFilterRow` 组件，覆盖肌群、分类、器械和目标，并放入 `FilterDrawer`。这样能复用同一套选中态、数量展示和横向滚动行为，避免每个维度各自实现。
- 低频筛选和核心筛选共用 `FilterDrawer`。相比默认展开面板，抽屉能保留完整能力，同时不改变列表区高度。
- 已选条件使用结构化数组保存 `key`、`label` 和 `clear` 处理函数。相比只拼接字符串，结构化数据可以支持单项移除，并减少后续扩展成本。
- 排序和每页数量保留原生 `select`，但移动到结果栏右侧。排序/分页是列表呈现控制，不属于动作属性筛选，视觉上应和筛选区分离。

## Risks / Trade-offs

- 横向 chip 在选项很多时需要滚动才能看到全部 → 只展示 facets 的前若干个高频选项，当前值仍通过已选条件 chip 展示。
- 筛选抽屉让条件入口更深 → 默认工具栏显示已选数量，抽屉内部展示已选 chips，降低用户遗忘当前筛选的风险。
- 单文件组件会增加局部子组件数量 → 保持子组件只服务动作库页面，不抽到共享层，避免过早泛化。
