# 聊天黑盒运行时错误修复

## 真实问题

最新 `docs/manual-llm-blackbox-flow-latest-report.md` 里剩余失败不是单纯测试用例过期：

- 多个纯动作推荐流程在 stream 前抛出 `Cannot read properties of undefined (reading '0')`，说明动作推荐 artifact 生成链路有运行时异常。
- `F05` 第 2 轮只补充“每周4练，每次45分钟”时，系统仍缺训练目标和器械，却直接推送了 `workout_plan`。
- 手动黑盒报告在非首轮失败后会停止当前 fixture，导致报告轮次数少于 fixture 总轮次，不利于区分真实失败和级联跳过。

## 调整思路

动作推荐仍保持“模型只看裁剪候选、服务端保存完整事实”的结构。聊天上下文中的 `providedExercises` 增加完整 `Exercise` 引用，模型可见 payload 仍由白名单字段生成；artifact 生成时使用完整动作对象补齐展示字段，避免半截对象被 `as Exercise` 强转后遗漏 `imageUrls`。

长期计划门控继续放在服务端归一化层：明确周期类请求如“6天训练计划”可以触发 plan；但笼统每周计划后只补频率和时长，仍不足以生成可执行计划，必须继续追问目标或器械。

## 关键改动

- `ExerciseContext.providedExercises` 保留完整 `Exercise`，`toExerciseRecommendationCandidatesFromContext()` 统一把上下文转为动作推荐候选。
- 动作推荐卡片图片字段改为安全读取，无图片动作不再让服务端崩溃。
- `canTriggerLongTermPlanFromContext()` 区分已有 plan 调整和 cadence-only 补齐，阻止空泛 weekly plan 提前推送。
- 手动 LLM 黑盒 runner 在任意轮失败后记录同流程剩余轮次为 skipped，报告轮次数保持完整。
- 增加确定性单测覆盖无图动作推荐候选、F05 第 2 轮门控和跳过原因生成。

## 验证方式

本次应通过 `tests/chat-service.test.ts`、手动 LLM runner 的无 key 跳过路径、`npm run typecheck` 和 `openspec validate fix-chat-blackbox-runtime-regressions --strict`。真实 `npm run test:llm` 仍需要用户确认 DeepSeek token 成本后再运行。
