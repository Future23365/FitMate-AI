# 2026-05-31 统一聊天意图决策流

## 真实问题

最新聊天 trace 暴露出一个结构性问题：同一轮对话里，用户可见回复、结构化动作触发、前端卡片生成和训练计划接口会各自解释意图。模型自然语言可能在追问，但 `assistant_action` 或旧 trigger 仍让前端继续调用推荐、routine 或 plan 生成接口；长期计划接口还可能用默认周期覆盖用户明确表达的 3 天、5 天或 6 天约束。

这个问题不能只靠 prompt 修。只补一句提示词仍然会留下多个事实源：回复正文、旧 trigger JSON、`assistant_action.intent`、前端 hook 和 `/api/ai/workout-plan` 都可能成为第二个编排器。

## 调整思路

本次把 `/api/chat` 收敛为唯一主编排入口，新增 `ResolvedChatIntent` 作为回复、动作触发、artifact 生成、trace 和前端事件的共同执行契约。LLM 仍负责自然语言理解，服务端只校验结构化结果是否自洽：追问模式不能触发 action，缺失字段不能生成卡片，plan/routine/action 类型不能冲突，引用不可用时不能执行 patch、替换或讲解。

当 resolved intent 自身冲突时，服务端只允许一次 resolved intent repair。repair 后仍不通过则降级为澄清回复，并禁止同轮卡片生成。

## 关键改动

- 新增共享 `ResolvedChatIntent` schema，覆盖 `action`、`responseMode`、`fieldSources`、`referenceRequirement` 和 `referenceResolution`。
- 聊天意图 schema 兼容旧字段，但 `type`、`workoutIntent` 和 `canTriggerAction` 统一从 resolved intent 派生。
- `/api/chat` 在服务端生成 recommendation、routine 和 plan artifact，并把结果作为 `artifact` / `artifact_failed` 事件返回；前端只展示服务端结果，不再二次调用生成接口补卡片。
- 历史 assistant 正文中的 `workout_plan_trigger`、`workout_routine_trigger`、`exercise_recommendation_trigger` 不再进入上下文事实，只保留展示清理能力。
- `PlanStrategy` 增加字段来源和默认假设，DomainPlanEngine 返回前校验周期、日历范围、周频率和引用来源与 strategy 一致。
