# Agent 引用目标解析合同收紧

时间：2026-06-05 13:09:04 CST

## 当前真实问题

在“继续 / 替换 / 调整已有对象”的引用型请求中，模型已经能通过 `inspectVisibleTrainingProposals(list_recent)` 查询当前会话是否存在可引用 `visibleTrainingProposal`。但当查询结果为空时，模型仍可能把引用型请求降级成相邻的新生成任务，再把 `searchExerciseResources` 的动作查询结果包装成新的 `visibleTrainingProposal`，并用“新一批”这类表达宣称完成了刷新。

这说明原合同没有把“引用目标不可确认”和“按新目标独立生成”区分得足够清楚。问题不在于缺少某个用户短句的服务端分支，而在于模型可见 prompt / observation 给了相邻语义降级空间。

## 原方案为什么不合适

旧的 `list_recent` observation 一边说明空 `facts[]` 不能支撑成功刷新或新方案生成，一边又允许模型“开始新的生成”。这会让模型在缺少引用对象时绕过缺口，直接查询动作库并输出结构化训练结果。

如果用服务端规则拦截某个短句、某个 `toolName` 或 `facts=[]` 组合，短期能挡住当前 trace，但会把自然语言语义判断放回服务端，违背 Agent 边界：LLM 负责语义理解，服务端只负责结构、权限、事实、resource 和 grounding。

## 调整思路

本次把修复收敛为“引用目标解析合同”：

- 通用 Agent prompt 说明引用型请求和独立生成请求是不同目标。
- 引用对象不可确认时，模型不得改写成相邻的新生成目标，也不得输出结构化结果声称已完成替换、刷新或调整。
- `inspectVisibleTrainingProposals(list_recent)` 空索引只表达当前可见事实状态，支持解释、澄清或请求补充目标，不再提供“开始新的生成”的宽松出口。
- `searchExerciseResources` observation 说明动作查询只证明查到动作事实，不证明当前 run 存在可刷新或可调整的上一轮对象，也不证明刷新已经完成。

## 关键改动

- 更新 `lib/server/agent-planners/prompts/agent-llm-prompt-config.ts`，补充通用引用目标解析规则。
- 更新 `lib/server/agent-tools/exercise-facts/inspect-visible-training-proposals.tool.ts`，收紧空 `facts[]` 的模型可见边界。
- 更新 `lib/server/agent-tools/exercises/search-exercise-resources.tool.ts`，说明动作查询结果不等于已有对象事实。
- 更新 prompt / tool observation / production replay 相关测试。
- 新增 OpenSpec change：`harden-reference-target-resolution-contract`。

## 边界说明

本次没有新增 `/api/chat`、runtime、validator、tool handler 或 renderer 的用户短语分流，也没有根据 `toolName`、`facts=[]` 或 `factCount = 0` 改写模型 action。具体短句只作为回归测试样例存在，不能反向决定生产规则。

## 验证方式

- `openspec validate harden-reference-target-resolution-contract --strict`
- prompt / observation / production chat replay 相关测试
- `npm run typecheck`
- `rg` 检查没有新增服务端关键词规则、自然语言模板路由、phrasing 特判或具体业务 `toolName` 语义分支
