# 2026-05-31 手动 LLM 黑盒流程测试

## 原方案为什么不合适

原 `npm run test:llm` 主要直接调用内部 prompt 分支，验证 `chatIntentResolution`、动作推荐生成和训练草稿生成等中间 JSON 输出。它能发现 prompt 契约漂移，但和首页聊天真实路径不一致：用户实际看到的是 assistant 文本和卡片推送结果，而不是内部字段。

根目录 `测试情况预览.md` 已经把验收目标收敛为 3 轮首页聊天黑盒流程，因此继续用调用点 fixture 会让测试目标偏离产品验收。

## 调整思路

将手动 LLM 测试改成服务端黑盒执行器：每个流程用例新建会话，同一流程内连续 3 轮沿用消息、summary、conversationContext 和最近 artifact 摘要。断言只看用户可见文本和卡片类型，不检查动作 ID、组数、训练时长精确值或计划细节。

## 关键改动

- 新增 `manual-tests/llm/flow-fixtures.ts`，用 9 个首页聊天流程覆盖动作推荐、刷新推荐、routine、plan、追问、语义切换、条件覆盖、非健身切回健身和最近卡片引用。
- 新增 `manual-tests/llm/blackbox-runner.ts`，复用 `prepareAiChatRequest` 和 `createAiChatResponse`，消费 NDJSON stream 并汇总 assistant 文本、`assistant_action`、trace id、conversation summary 和 token usage。
- 重写 `manual-tests/llm/assertions.ts`，只做用户可见文本、内部字段泄漏和卡片类型断言。
- 更新 `scripts/run-manual-llm-tests.mjs`，输出 9 个流程、27 轮、约 78,900 token 的预估，并把报告写到 `docs/manual-llm-blackbox-flow-latest-report.md`。
- 更新 `docs/manual-llm-consistency-tests.md`，说明新的黑盒测试边界、报告路径和维护方式。

## 验证情况

- `npm run typecheck` 通过。
- `npm run test` 通过，确认默认测试不会执行真实 LLM 黑盒流程。
- `DEEPSEEK_API_KEY= npm run test:llm` 通过，确认缺配置时会清晰跳过并生成 27 轮跳过摘要。
- 真实 `npm run test:llm` 因外部 DeepSeek 数据传输风险被安全审查拒绝，未在本次执行真实模型请求。
