# 旧 artifact 引用恢复

## 原问题

聊天链路会先在 `/api/chat` 中把“这个”“刚才那套”等表达解析为 `ReferenceResolution`，再由前端触发 `/api/ai/workout-plan` 生成长期计划。两次请求之间，聊天自动保存可能把同一 routine 写成新的 `ConversationArtifact` revision，并把旧 artifact 标记为 `superseded`。

原方案只允许 `getArtifactPayload` 读取 `status = active` 的 artifact。这个权限边界本身正确，但当后续请求还带着旧 revision id 时，系统会把合法引用误判为 `not_found`，最终显示受控工具调用错误。

## 调整思路

不放宽 payload 读取权限，也不允许从 `conversationSummary` 反向重建训练内容。改为在 artifact service 中新增一个专用读取入口：当传入 id 是当前用户可访问的旧 revision 时，沿同一用户、同一会话、同一 kind 的 revision lineage 找到当前 active artifact，再读取并校验 payload。

## 关键改动

- 新增 active revision 解析读取能力，保留原 `getArtifactPayload` 的严格 active-only 语义。
- 长期计划的 DomainPlanEngine 分支改用新的受控读取入口，避免旧 revision id 直接中断。
- trace 中记录原始引用 id、最终 active id 和 revision 解析状态。
- 补充测试覆盖 active 直读、superseded lineage 恢复、无关/归档 artifact 失败，以及长期计划复用旧 id 时不回退到模型自由生成。

## 结果

用户在聊天中刚生成或刚修改训练卡片后，继续说“今天明天后天都练这个”这类请求时，即使前端携带的是旧 revision id，服务端也能在权限范围内恢复到当前 active payload 并继续生成长期计划。
