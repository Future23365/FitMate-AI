# Agent 终态 Grounding 合同硬化

时间：2026-06-05 18:10:38 CST

## 当前问题

`/api/chat` trace 显示，Planner 在已经执行 `inspectVisibleTrainingProposals(read_recent)` 并拿到当前 run 的训练事实后，又输出了无 `usedToolResultIds`、无 `usedResourceRefs`、空 `visibleOutputs[]` 的成功 `final_answer`。正文承诺后续还要查询热身和拉伸动作，但 runtime 已经把该 `final_answer` 当成本轮终态投影，导致用户看到“请稍等”后实际没有继续 tool 调用，也没有生成可见训练编排。

原有方案只校验了显式引用的 tool result、resource 和 `visibleOutputs[]` 结构；如果模型完全不引用任何 grounding，validator 没有稳定合同可以拒绝，只能依赖 prompt 约束模型自觉遵守。

## 调整思路

本次把问题归类为 Agent core terminal contract 缺口，而不是单个业务 tool bug。服务端不读取用户原文、不分析 assistant 正文，也不基于具体 `toolName` 做分流；只在当前 run 已经存在 tool result 且成功 `final_answer` 完全没有 grounding 时拒绝该 terminal action，并通过 repair observation 告诉 Planner 合法恢复方式。

## 关键改动

- `Action Validator` 增加通用 guard：工具执行后，成功 `final_answer` 必须至少具备 `usedToolResultIds`、`usedResourceRefs` 或 `visibleOutputs[]` 之一。
- repair details 使用结构化恢复方向，允许继续合法 `tool_call`、引用 satisfied tool result、引用 consumable resource、输出合法 `visibleOutputs[]`、`ask_user` 澄清或失败收口。
- 默认 Agent prompt 升级到 `agent-action-v11`，明确 `final_answer` 是当前 run 终态，不会触发回复后的自动 tool 调用。
- `inspectVisibleTrainingProposals` 和 `searchExerciseResources` 的模型可见说明同步表达事实读取 / 查询与最终训练输出分离。
- 生产聊天 replay 回归覆盖原始失败类别和等价表达，确认被拒绝的 `final_answer.content` 不会提前渲染，repair 后仍可继续合法 tool 调用并输出训练结构。
