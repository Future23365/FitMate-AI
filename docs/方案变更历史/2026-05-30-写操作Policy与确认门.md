# 2026-05-30 写操作 Policy 与确认门

## 当前问题

聊天链路已经能保存 artifact、解析引用并对训练草稿做局部 Patch，但“能不能改”和“要不要用户确认”还没有统一边界。高影响操作例如覆盖已保存 routine、批量修改未来 schedule、改变周频率、重排日历、写入长期健康限制，如果只靠局部服务各自判断，后续很容易出现 AI 一步写入用户长期数据的问题。

## 调整思路

把训练内容校验和写操作授权拆开：

- `Validator` 继续判断训练内容是否有效、动作是否来自候选集合。
- `PolicyEngine` 判断当前操作是否允许、是否需要确认，以及最安全的 `safeScope`。
- `ConfirmationGate` 对高影响操作生成短期签名 token，绑定 userId、目标 id、scope、operation 和 diff 摘要。

这样即使模型理解了用户意图，也只能通过服务端 policy、确认门和校验后再进入持久化入口。

## 怎么做的

- 新增 `lib/shared/policy-confirmation/schema.ts`，定义 `PolicyCheckResult`、policy reason、safeScope、confirmation token 和确认请求结构。
- 新增 `lib/server/policy-confirmation/policy-engine.ts`，集中处理 artifact、routine、schedule、user memory、plan change 和 WorkoutPatch 的策略判断。
- PatchEngine 接入 `policy_check` 和 `confirmation_gate` trace；`artifact_only` 单动作修改仍可直接生成新 revision，高影响 scope 在确认前只返回确认问题和 diff 摘要。
- 用户记忆写入复用 memory policy，长期限制和健康/不适信号保持 `pending_confirmation`。
- 补充 token 绑定 diff/scope/target、过期拒绝、已完成历史阻断、未来安排确认等测试。

## 结果

当前高影响写操作已经有统一的服务端策略出口，并能在 AI Trace 中看到 `policy_check` 与 `confirmation_gate`。已完成训练历史默认 blocked；未保存聊天草稿的单动作替换仍保持低摩擦，只创建 artifact revision，不覆盖 saved routine 或 future schedule。
