# Agent 合同修复循环

时间：2026-06-02 18:16:05 +0800

## 原方案为什么不合适

此前 Agent runtime 已经分散处理过几类模型抖动：保存前提前 `final_result.generated`、保存后漏填 generated 字段、重复不可重试工具失败等。这些补丁能覆盖单个 trace，但问题形态仍然围绕同一个根因：模型违反的是 Agent 决策合同，而 runtime 没有统一的结构化反馈、预算和最终事实收口协议。

继续按失败形态追加 helper 会带来三个问题：

- 新旧恢复逻辑并存，难以判断某次恢复来自哪条路径。
- 失败 tool result、`satisfied=false` result 和真实成功资源容易在 dependency graph 中混淆。
- 黑盒报告只能看到最终失败或成功，无法稳定说明是 recovered、fused、unrecoverable 还是 projected。

## 调整思路

本次把恢复逻辑收敛到薄的 `AgentDecisionFeedback` 协议。runtime 只描述为什么拒绝模型决策、当前有哪些已登记资源、缺什么资源、推荐下一步工具和输入；它不重新解释用户自然语言，不新增 tool 能力合同，也不替代权限、Policy、Validator 或持久化边界。

修复循环增加独立预算和重复失败熔断。可恢复 feedback 进入下一轮模型上下文，不可恢复 hard boundary、预算耗尽、多候选事实无法唯一确定或权限/Policy 类失败直接终止。

## 关键改动

- `contracts.ts` 新增 `AgentDecisionFeedback`、feedback code、模型可见摘要、repair budget 和 `AgentRepairSummary`。
- `runtime.ts` 将 parse failure、final result 未登记资源、工具 schema/依赖失败、`satisfied=false`、重复工具失败统一挂到 `AgentToolResultRecord.decisionFeedback`。
- dependency graph 只把 `status=success` 且 `fulfillment.satisfied !== false` 的 tool result 登记为可消费资源；feedback 和失败结果只保留为错误事实。
- `generated` / `patched` / `completed_operation` 的最终结构化事实必须来自当前 run 已登记写工具结果；保存成功且唯一时可从写工具投影，多个候选不猜测。
- prompt modules 只新增如何消费 `AgentDecisionFeedback` 的说明，不引入关键词分流、同义词匹配或服务端语义纠偏。
- trace、stream 和黑盒 runner 新增 `repairFeedbackCodes`、`repairTurnCount`、`finalProjectionSourceToolResultId`、`unregisteredResourceReferences`、`fusedFailureCount` 和 `repairBudgetExhaustedReason`。
