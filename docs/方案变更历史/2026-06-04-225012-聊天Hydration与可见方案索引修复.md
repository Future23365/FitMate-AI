# 聊天 Hydration 与可见方案索引修复

时间：2026-06-04 22:50:12 CST

## 当前真实问题

`/api/chat` 在服务端 hydration saved conversation 后，会把数据库历史消息和本次请求的 `latestUserMessage` 合并。原实现为了避免同一条最新用户消息重复进入上下文，只检查“历史里最近一条 user 消息内容是否等于 `latestUserMessage`”。当上一轮已经有 assistant 回复后，用户再次发送相同文本，例如连续两轮都说“不要”，这条新 user turn 会被误判为重复并被吞掉。

同一条 trace 还暴露了另一个边界问题：`run.metadata.recentVisibleTrainingProposals` 直接包含上一套可见训练方案的完整 `exerciseItems`。这和现有 prompt / tool manifest 中“metadata 只提供 `factRef` / `messageId` 索引，完整事实必须通过 `inspectVisibleTrainingProposals(read_recent)` 导入”的合同不一致，模型可以绕过正式 read/search 流程复用旧动作。

## 调整思路

本次不做服务端自然语言判断，不识别“不要”“换一批”等短句，也不改 Agent runtime。修复只落在两个确定性边界：

- 消息合并按消息轮次判断，只在 saved conversation 最后一条消息本身是同内容 `user` 时去重；如果最后一条是 `assistant`，同文本也必须追加为新 user turn。
- `recentVisibleTrainingProposals` 注入 Agent run metadata 前先经过安全投影，只保留引用、版本、方案类型、section 数量和可复用 training 动作数量，不再暴露完整动作项、处方、schedule 或展示详情。

## 关键改动

- `appendLatestUserMessageIfMissing()` 从“最近一条 user 文本去重”改为“最后一条消息同内容 user 去重”。
- 新增 `toVisibleTrainingProposalMetadataSummary()`，作为 `/api/chat` metadata 的唯一安全投影入口。
- `restoreRecentVisibleTrainingProposalsForRun()` 改用 metadata summary，不再把 fact store 完整 summary 直接传给 Planner。
- 补充回归测试，覆盖 assistant 已回复后的同文本新 user turn、真实同条 user 幂等、metadata 不含 `exerciseItems` / `prescription` / `imageUrl`，以及 fact store 投影边界。

## 为什么不是局部补丁

如果只针对“不要”写服务端分支，会把自然语言语义判断重新拉回服务端，后续“换一批”“不要这个”“再来一组”仍会重复出现同类问题。本次修的是消息序列和模型可见事实投影这两个稳定合同，不依赖用户具体措辞。
