# 动作替换候选选择链路修复

记录时间：2026-06-01 14:47:06 CST

## 原问题

用户在首页聊天里要求“把某个动作换成别的”时，服务端已经能通过 ReferenceResolver 找到训练卡片和目标动作，但后续链路有两个断点：候选动作只出现在自然语言正文里，前端不会也不应该从 Markdown 正文解析按钮；用户下一轮输入候选动作名后，服务端又可能把替换意图降级为 `answer_only`，没有执行 `replace_exercise` Patch。

这会造成用户可见回复承诺会更新训练内容，但实际没有返回 `assistant_suggestions`、`workout_patch` 或新的 artifact revision。

## 调整思路

动作替换被收敛为服务端结构化多轮状态：

- `exercise_replacement` 即使模型漏填或误填 `action.kind = "none"`，也恢复为引用型 action，并要求 artifact 引用解析。
- 已定位 source exercise 但未指定 replacement exercise 时，服务端返回 `assistantSuggestions`，并保存短期 `pendingReplacementSelection`。
- 下一轮用户点击候选按钮，或手动输入 pending 候选集合中的唯一动作名时，服务端用 pending 状态补齐 source 和 replacement，再进入 `WorkoutPatchEngine`。
- 替换执行仍只通过 `replace_exercise` Patch 写入新的 artifact revision，不让前端或正文文本直接执行修改。

## 关键改动

- 会话上下文新增短期 `pendingReplacementSelection`，包含 artifact、source exercise、候选 exercise ids、创建和过期时间。
- `/api/chat` 请求继续发送服务端结构化上下文，保证用户快速点击候选时下一轮也能消费 pending 状态。
- `workout-patch-chat-service` 在缺少替代动作时返回候选建议，不再自动选择替代动作直接应用 Patch。
- `WorkoutPatchResult` 支持携带 `assistantSuggestions` 和 pending selection，确定性回复会同步更新前端上下文。
- 测试覆盖候选按钮、pending 候选消费、resolved intent 恢复、以及未执行 Patch 时不虚假承诺卡片已更新。
