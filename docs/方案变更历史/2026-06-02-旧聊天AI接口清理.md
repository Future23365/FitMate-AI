# 旧聊天 AI 接口清理

记录时间：2026-06-02 13:35:50 CST

## 原方案为什么不合适

Tool-first `AgentOrchestrator` 已经成为 `/api/chat` 生产主链，但代码里仍保留旧聊天 AI 独立接口、前端旧 helper、旧 trigger JSON parser 和旧正向测试合同。这会让后续开发继续误以为存在第二套生成入口：前端可以绕过 Agent stream/result，再调用旧接口生成计划、routine 或动作推荐卡片。

这类残留的问题不只是多几个文件。它会破坏“LLM 负责语义、服务端只做契约校验”的边界，因为旧接口内部仍可基于旧 intent / summary-only 材料重新组织计划或推荐生成。

## 调整思路

本次清理选择删除旧执行面，而不是保留兼容代理或返回 410。聊天计划、routine、动作推荐、Patch 和建议回复统一从 `/api/chat` Agent-first 合同表达。推荐刷新要么作为新的自然语言消息交给 Agent，要么对已有 Agent result 做确定性分页、去重和排除已反馈动作。

## 关键改动

- 删除旧聊天 AI 独立 Route Handler 和只服务这些 route 的计划/推荐生成服务。
- 删除前端旧 route helper 和旧 trigger JSON parser。
- 删除旧 `reference-resolver-service`、旧 `workout-patch-chat-service` 和旧 shared `referenceResolution` schema；artifact 引用和 Patch 入口改由 Agent artifact tools、`WorkoutEditPlan`、Patch tools 和 `workout-patch-engine` 表达。
- 前端新流只消费 `agent_execution_result`、artifact / patch / suggestion 事件和 done metadata。
- 将历史 trigger 清理限制为纯展示文本剥离，不解析 intent，不触发卡片。
- 更新 `docs/legacy-intent-allowlist.md`，把 active Route Handler、前端新流、生产导出、领域服务和当前 OpenSpec 主规格纳入扫描范围。
- 新增架构级防回归测试，断言旧 route、旧 helper、旧 parser 和旧主规格要求不能回到生产路径。

## 验证边界

本次验证重点不是重跑真实模型，而是证明旧执行面无法被生产聊天触发。自动化覆盖旧接口缺席、前端调用缺席、旧 parser 缺席和当前主规格缺席。完整验证结果以本次提交前的 `npm test`、`npm run typecheck`、`npm run build` 和 OpenSpec strict validate 为准。
