# 2026-05-30 RAG 模型 Payload 瘦身

## 当前真实问题

RAG 混合检索接入后，服务端可以召回和排序更多动作候选，但模型请求也开始携带更多候选上下文。短句对话会先触发聊天模型，再触发动作推荐或训练编排模型；如果候选 payload 里包含图片、英文名、中文难度冗余字段、长推荐原因和重复候选池，单轮 token 会从之前约 6k 上升到 1w 甚至 2w 以上。

## 调整思路

把“服务端完整动作对象”和“模型需要理解的候选摘要”拆开。服务端仍保留完整对象，用于最终卡片图片、持久化、校验和 trace；模型只接收完成选择和编排所需的字段，例如动作 ID、中文名、分类、难度、器械、肌群、风险标签、目标标签、来源和分数。

## 怎么做

- 动作推荐模型的 `candidateExercises` 删除 `imageUrl/imageUrls/images`、`nameEn`、`levelZh` 和完整 `candidateReasons`。
- 训练草稿模型的候选 payload 删除展示和重复元数据，只保留编排语义字段，并把单类候选上限从 40 降到 16。
- 新增 OpenSpec change `trim-rag-model-payload`，记录模型 payload 预算边界。
- 补充测试，确认模型请求不再包含图片、英文名、中文难度冗余字段和长原因，同时最终动作推荐卡片仍从服务端完整动作对象补齐图片。

## 结果

已通过相关自动化测试和 TypeScript 类型检查。该调整不会改变 RAG 召回结果、API 响应结构或用户可见卡片展示，只降低模型输入上下文体积。
