# 2026-06-02 22:24:06 CST 动作库服务端分页查询

## 当前问题

动作库页面和动作编排页右侧动作库都已经按 `page/pageSize` 请求 `/api/exercises`，但服务端 `listExercises()` 仍先读取完整 `Exercise[]`，再在 Node.js 内存里完成筛选、排序和分页。随着动作详情、教学步骤、图片字段和 embedding 增加，这会让普通列表请求承担完整动作库的内存成本。

## 调整思路

把用户可见动作库列表和 AI 候选搜索拆开处理。列表路径只需要当前页摘要，因此下推到 repository 的数据库查询；AI `searchExercises()` 仍保留完整动作集合和 hybrid search 逻辑，避免把本次性能问题扩大成语义搜索重构。

## 关键改动

- 新增列表专用 repository 查询，使用 Prisma `where/select/orderBy/count/take/skip` 读取当前页 `ExerciseListItem` 字段。
- `/api/exercises` 背后的 `listExercises()` 不再调用 `listExerciseRecords()`，只负责分页响应组装。
- facets 改为数据库聚合统计，标量字段使用 Prisma `groupBy`，数组字段使用受控白名单 SQL `unnest`。
- 动作编排页右侧动作库继续复用同一 `/api/exercises` 契约，因此阶段、分类、肌群、器械等筛选自动受益。
