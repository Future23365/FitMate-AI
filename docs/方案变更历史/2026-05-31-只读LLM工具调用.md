# 只读 LLM 工具调用

## 原方案为什么不合适

聊天链路已经有 `ReferenceResolver`、`searchArtifacts`、`getArtifactPayload`、`getExerciseById`、`searchExercises` 等只读能力，但它们分散在固定服务端分支里。用户追问“为什么推荐这个动作”“之前那套计划为什么这样安排”时，最终回复模型只能依赖 `conversationSummary` 和轻量 artifact 摘要，无法在服务端权限边界内按需补查真实数据。

继续为每种追问堆固定分支会让 `chat-service.ts` 变得越来越难维护，也不利于 trace 复盘工具选择、失败回退和额外模型调用成本。

## 调整思路

新增 `lib/server/ai/tools/` 作为统一只读工具层。LLM 只负责通过受控 JSON 协议选择一个只读工具或停止；工具白名单、Schema 校验、权限上下文、执行、摘要、预算和 trace 全部由服务端完成。

首版只开放四个读工具：

- `searchArtifacts`
- `getArtifactPayload`
- `getExerciseById`
- `searchExercises`

生成训练计划、生成 routine、动作推荐、Patch 和保存类写操作仍然走现有 `resolvedIntent`、Validator、PolicyEngine、ConfirmationGate 和领域服务，不允许 tool loop 改写执行决策。

## 关键改动

- 建立 `ControlledReadTool`、`ControlledToolContext`、`ControlledToolResult`、统一错误结构和只读 registry。
- 增加 tool executor，集中处理未知工具拒绝、Zod Schema 校验、执行失败归一化、耗时统计和 `tool_call` trace。
- 增加 `ReadonlyToolDecision` JSON 协议，不使用标准 `tools` / `tool_choice` 作为首版运行时契约。
- 增加 `runReadonlyToolLoop`，默认 `maxSteps = 3`、最多 3 次额外 decision 模型调用、总耗时 8 秒、bundle 预算 6000 字符。
- 工具输出进入模型前统一摘要化，artifact payload 摘要覆盖 `exercise_recommendation`、`routine`、`plan` 和 Patch 结果摘要。
- `/api/chat` 在最终回复前接入可选 `ReadonlyToolContextBundle`，并通过 `ENABLE_READONLY_LLM_TOOLS` 默认关闭。
- AI Trace 新增 `tool_decision` step，并在 `/dev/ai-traces` 中展示工具决策、跳过原因和执行摘要。

## 怎么做的

只读工具层复用现有 artifact service 和 exercise service，不新增数据库表，不改变 Prisma Schema。`getArtifactPayload` 在引用解析已 resolved 时还会受 `allowedArtifactIds` 限制，避免模型绕过候选边界读取其他 artifact。

聊天编排的触发矩阵只允许历史 artifact 解释、动作详情补查、推荐理由解释和计划理由解释进入 tool loop。只要当前路径已经由引用澄清、Patch、动作讲解或生成型 artifact 流程确定性处理，就记录 skipped reason 并跳过 tool loop。

## 验证结果

- 新增 `tests/readonly-tools.test.ts` 覆盖 registry、executor、decision、摘要、feature flag 默认关闭、触发矩阵和 prompt 上下文边界。
- 更新 `tests/ai-trace-viewer.test.ts` 覆盖 `tool_decision` 分组展示。
- 已运行相关测试、完整测试、类型检查和构建验证。
