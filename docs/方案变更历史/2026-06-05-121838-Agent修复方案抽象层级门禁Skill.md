# Agent 修复方案抽象层级门禁 Skill

记录时间：2026-06-05 12:18:38 CST

## 当前真实问题

Agent 修复经常从单个 trace、用户原话、tool result 或模型输出失败开始。如果没有单独门禁，后续方案容易把“这次 case 发生了什么”直接写成通用 prompt、runtime 或服务端生产规则，例如按用户短句、具体 `toolName`、字段组合或 phrasing 做语义分流。这会破坏项目既有边界：LLM 负责自然语言语义理解，服务端只管结构、权限、resource、policy、projection 和 grounding 等确定性合同。

## 调整思路

新增项目级 Codex Skill `agent-fix-abstraction-gate`，专门在开始实现 Agent / prompt / tool 修复或审查 OpenSpec change 前，判断修复方案是否放错抽象层级。

它不替代已有两个治理 Skill：

- `agent-tool-change-governance`：判断 Agent tool / core / production 能改哪里、不能改哪里。
- `agent-prompt-contract-governance`：审查模型实际可见 prompt / model input 合同。
- `agent-fix-abstraction-gate`：审查修复方案是否把失败证据、业务实例或测试样例错误升格为通用生产规则。

## 关键改动

- 新增 `.codex/skills/agent-fix-abstraction-gate/SKILL.md`，写清触发条件、必读上下文、抽象层级分类、禁止方案、正确修复层级和固定输出格式。
- 新增 `.codex/skills/agent-fix-abstraction-gate/agents/openai.yaml`，让 Codex UI 能展示该 Skill。
- 新增 OpenSpec change `add-agent-fix-abstraction-gate-skill`，用 spec 固化该 Skill 的触发场景、违规暂停要求和通过审查输出要求。

## 怎么做的

门禁输出被设计成两个固定结论：

- 发现违规时输出 `结论：暂停执行`，并给出违反条款、证据、问题层级、正确修复层级和继续条件。
- 未发现违规时输出 `结论：可继续`，并说明抽象问题类型、通用合同修复、业务 tool 局部说明、回归测试样例和服务端语义分流检查。

本次只新增 Skill 和治理文档，不修改 Agent runtime、生产 prompt、tool、`/api/chat` 或数据库结构。
