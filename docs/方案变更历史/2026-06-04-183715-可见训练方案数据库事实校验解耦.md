# 可见训练方案数据库事实校验解耦

时间：2026-06-04 18:37:15 CST

## 背景

`visibleTrainingProposal` 是当前 `final_answer.visibleOutputs[]` 中承载动作推荐、单次训练和计划的用户可见训练事实。旧实现里，validator 和 renderer 会从本轮 `toolResults` 中按具体 `toolName` 收集动作来源：`searchExerciseResources` 的分组结果、`inspectVisibleTrainingProposals` 的历史事实结果，或 `visible_training_proposal_fact` resource 摘要。这让“动作是否真实存在、当前是否发布、section 是否合法”和“模型是否刚好调用过某个具体 tool”混在一起。

这个设计的问题是扩展成本和安全边界都不清晰：后续新增动作查询、动作解析或候选推荐 tool 时，即使最终输出的 `exerciseId` 已经是数据库中的发布态动作，也要同步修改 `visibleTrainingProposal` validator / renderer 的 toolName 白名单。

## 调整思路

本次采用 `async terminal output validator` 方案。`agent-core` 只扩展通用 validator 接口，支持异步返回有限 `terminalOutputValidation` metadata；生产装配层注册的 `visibleTrainingProposal` validator 注入只读数据库事实服务。这样 runtime 会在 `final_answer` 结束前完成动作事实校验，未经校验的 `visibleOutputs[]` 不会进入 Response Renderer、fact bridge 或聊天历史保存。

## 关键改动

- 新增 `visible-training-proposal-exercise-facts.ts`，按最终 `exerciseItems[*].exerciseId` 去重批量读取动作，并校验动作存在、`isPublished = true`、`allowedSections` 覆盖输出 `section`。
- `visible-training-proposal-validator.ts` 不再读取 `toolResults` 或具体业务 `toolName`，只保留 payload schema 校验和数据库事实校验。
- `visible-training-proposal-renderer.ts` 改为消费 validator 返回的 canonical 动作摘要，删除从 `searchExerciseResources` / `inspectVisibleTrainingProposals` tool output 拼详情的分支。
- `visible-training-proposal-fact-store.ts` 读取历史可见训练事实时复核当前数据库状态，历史事实不再绕过下架动作或 section 变化。
- `agent-llm-prompt-config.ts` 将模型可见 `exerciseId` 来源说明从具体 toolName 绑定改为“当前 run 可见的发布态动作事实，最终由服务端数据库复核”。

## 结果

最终训练方案合法性现在由 PostgreSQL 动作事实和结构化 validator 决定，`searchExerciseResources` 继续只是帮助模型发现动作事实的只读 tool。新增同类动作查询能力时，不需要再修改 terminal output core、validator 或 renderer 的 toolName 白名单。
