# 前端首包与动作资源性能优化

时间：2026-06-02 21:29:11 CST

## 问题

首页聊天虽然已经有 App Router 路由级拆分，但首屏仍同步加载 Markdown 渲染、训练计划卡、动作编排卡、动作推荐卡和完整 Zod schema。动作编排页和训练执行页也同步加载动作详情 Sheet 等交互后面板。与此同时，`/api/exercises` 列表接口返回完整动作详情，动作图片又在 `images.unoptimized: true` 下直接依赖原始图片传输。

这些问题会让首屏 JS、列表响应和图片解码成本同时偏高，后续局部懒加载也难以证明真实收益。

## 调整思路

先建立可重复统计脚本，再把低频重组件、客户端 schema、动作详情和主应用 shell 副作用拆到真实需要的边界。动作列表改为摘要 DTO，完整详情按 id 读取并缓存。图片策略选择 Next image optimizer，保留现有本地图片 Route 的安全边界。

## 关键改动

- 新增 `npm run perf:frontend`，从 `.next` client-reference manifest 输出关键路由 raw/gzip 和 chunk 清单。
- 首页 Markdown 和 artifact cards 改为动态加载，并在 `artifact_generating` 时预加载对应卡片。
- 首页聊天控制器改用轻量 guard 和轻量 conversation context，避免首屏加载完整训练计划 Zod schema。
- 动作编排页和训练执行页的动作详情 Sheet 改为按需加载，提供 loading/error drawer。
- `/api/exercises` 返回 `ExerciseListItem` 摘要，动作库右侧详情按 id 拉完整 `Exercise` 并缓存。
- `next.config.ts` 启用 Next image optimizer，列表图片不再长期依赖原始大图直传。
- 主应用页面迁移到 `(main)` route group，`/training` 和 `/dev/ai-traces` 不再挂载侧栏历史读取和导航副作用。

## 结果

生产构建统计显示：

- `/` gzip 从 179.9 KB 降至 59.1 KB，下降 120.8 KB。
- `/training` gzip 从 77.1 KB 降至 70.1 KB。
- `/dev/ai-traces` gzip 从 79.7 KB 降至 73.6 KB。

详细前后数据见 `docs/performance/frontend-performance-before.json` 和 `docs/performance/frontend-performance-after.json`。
