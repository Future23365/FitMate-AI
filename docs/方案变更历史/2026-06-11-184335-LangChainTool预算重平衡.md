# LangChain Tool 预算重平衡

时间：2026-06-11 18:43:35 CST

## 背景问题

生产 `/api/chat` 已迁移到 LangChain Agent Runtime 后，`maxToolCalls = 5` 被当成所有业务 tool 共用的整轮预算。这个设计能防止无限循环，但会让第一个 tool 独占全部调用次数：如果模型反复调用同一个 tool，后续 tool 没有一次合法调用或修正空间。

问题不在单个业务 tool handler，而在 runtime 预算语义过粗。共享小预算把“整轮安全熔断”和“单个 tool 的公平调用上限”混成了一个字段。

## 调整思路

本次把预算拆成两层：

- `maxToolCalls = 20`：整轮业务 tool 总调用安全上限，防止跨多个 tool 的无限循环。
- `maxToolCallsPerTool = 2`：单个业务 tool 单轮最多调用两次，表达首次调用加一次模型修正空间。

per-tool 限制使用 LangChain 原生 `toolCallLimitMiddleware`，由 runtime 根据当前 business tool wrappers 自动生成，不在业务 handler、`/api/chat` route 或 prompt 中写具体业务分支。

`reportAgentActivity` 继续走独立 `maxActivityReports`，不占业务 tool 总预算，也不参与 per-tool business limit。

## 关键改动

- 集中配置新增单 tool 调用上限，并把业务 tool 总预算调为 20。
- LangChain runtime 在 `createAgent` middleware 中接入每个业务 tool 的 `toolCallLimitMiddleware`。
- 保留项目原有总预算熔断，超过 20 次业务 tool call 时仍不执行后续 handler。
- 模型可见 system prompt 同步说明总预算、单 tool 上限和 activity report 独立预算。
- 测试覆盖单 tool 第三次调用被拦截、跨多个 tool 超过总预算被熔断，以及 prompt / config 预算同步。

## 方案取舍

没有把“是否重试”做成服务端自然语言判断，也没有在业务 tool handler 中各自计数。这样可以保持 tool handler 只负责业务能力，runtime 负责通用预算合同，LangChain middleware 负责 provider tool call 级别的拦截。

这个方案比单纯把 `maxToolCalls` 从 5 调大更稳：调大总预算只会延后问题，per-tool 上限才能避免单个 tool 独占整轮预算。

## 结果

预期效果是每个业务 tool 在同一轮中最多被调用两次；如果某个 tool 达到上限，模型仍可使用其他业务 tool 或结构化终态收口。整轮最多允许 20 次业务 tool call，避免 tool catalog 扩大后出现无界循环。
