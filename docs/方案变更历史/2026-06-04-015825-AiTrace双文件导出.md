# 2026-06-04 01:58:25 CST AiTrace 双文件导出

## 原问题

`/dev/ai-traces` 的「保存全链路log」原本把结构化摘要、Raw trace 和长文本都写进 `codex_logs/ai_trace_log.js`。这让默认排查入口很重；如果继续靠长度硬截，又会丢掉 prompt 尾部约束、tool observation 尾部反馈或模型 JSON 结尾，影响排查模型行为 bug。

## 调整思路

默认报告应该服务于快速定位：先看 loop、step、tool、error code、token usage、response summary 和关键 id。长 prompt、model input、observation、raw response 等只在需要时按引用读取。

## 关键改动

- 「保存全链路log」改为覆盖写入两份文件：
  - `codex_logs/ai_trace_log.js`：轻量报告，保留结构化摘要和 `contentRef`。
  - `codex_logs/ai_trace_texts.jsonl`：长文本映射，一行一个脱敏长文本记录。
- 报告中的长文本引用包含 `contentRef`、`path`、`kind`、`originalLength`、`hash` 和 `preview`。
- 两个导出文件头部都加入查询说明，默认先读报告；需要长文本时用 `rg '"contentRef":"text_0001"' codex_logs/ai_trace_texts.jsonl` 定位。
- 服务端继续脱敏，并额外防止 `payload`、`handler`、`database`、`tool_output` 等敏感路径通过长文本映射绕过脱敏。

## 2026-06-04 02:08:45 CST 修正

第一次实现只抽离了长字符串，但默认报告仍保留完整 `rawTrace` / `trace` 和过重的 `runtimeTraceEvents`，导致 `ai_trace_log.js` 仍有数千行。修正后默认报告不再内联完整 Raw trace，而是使用 `traceSummary`、step summary 和轻量 runtime event 摘要；长文本映射按 hash 去重，同一段 prompt 或 observation 多次出现时只保存一条内容，并记录出现路径。

## 2026-06-04 02:21:11 CST 修正

再次检查 30 多轮对话保存结果时发现，`ai_trace_texts.jsonl` 仍然只有很短内容。根因不在导出层，而是 `DeepSeekModelAdapter.createRequestTrace()` 在进入 `AiTraceStore` 前已经把 `requestBody.messages[].content` 按 800 字符摘要化，导出层只能保存这个摘要。

修正后，真实发送给模型的 request body 不变；adapter 只改变开发态 request trace 的诊断表示：超过摘要阈值的 message content 保存为小块 `trace_long_text` envelope，导出层识别后合并 chunks，写成一条 long text mapping。默认报告仍只保留 `contentRef`，不会把 chunks 或完整长文本重新塞回 `ai_trace_log.js`。

## 边界

本次只修改开发态 trace 诊断和导出格式，不修改 `/api/chat`、Agent runtime、PlannerPort、ToolRegistry、Policy Guard、ResourceStore、Response Renderer、模型实际输入或用户可见聊天协议。
