# 2026-05-31 建议回复与执行意图解耦

## 真实问题

最新聊天 trace 里，意图模型在“你好”这类非执行场景已经返回了可展示的 `suggestedReplies`，但同一个 JSON 里带了 `workoutIntent:null`。旧的 `chatIntentSchema` 把整包输出作为一个原子 schema 校验，`workoutIntent:null` 一失败，服务端就直接替换成 `createFallbackChatIntent()`，最终把本来合法的建议回复按钮清空。

这个问题说明交互层和执行层被绑在了同一个失败边界上。建议回复只是用户可见的补充入口，不应该因为非执行字段漂移而消失；但动作推荐、routine、plan 等内部动作仍然必须依赖合法的结构化执行意图。

## 调整思路

本次把聊天意图解析拆成两个层次：

- 交互层：独立解析和过滤 `suggestedReplies` / `suggestedQuestions`，只保留非空、长度合法、非疑问句的结构化按钮文本。
- 执行层：`workoutIntent` 仍必须通过 `workoutPlanIntentSchema`，只在非执行场景允许 `null` 归一化为缺省内部值。

如果模型输出的交互层可恢复，但执行层缺失或非法，服务端会保留合法建议回复，同时把 `canTriggerAction` 压回 `false`，并把 `workoutIntent` 记录为阻断字段，防止内部动作靠兜底 intent 误触发。

## 关键改动

- `parseChatIntentModelOutput()` 成为模型意图输出的统一解析入口，负责 schema 解析、交互层恢复、执行层阻断和诊断信息生成。
- `chatIntentSchema` 支持非执行场景的 `workoutIntent:null` 归一化，同时对建议回复做独立过滤。
- 意图 trace 新增归一化、部分恢复、最终可见建议回复、被清空原因和执行阻断原因，后续排查能区分“模型没给按钮”和“按钮被服务端过滤”。
- Prompt 明确非执行场景可以省略或返回 `workoutIntent:null`，执行场景必须提供合法结构。
- 回归测试覆盖问候建议回复、执行型缺失 `workoutIntent`、非法建议回复过滤，以及 `suggested_replies` 流事件编码。
