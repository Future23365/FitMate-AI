# 2026-05-30 聊天引用解析

## 真实问题

聊天卡片已经保存为 `ConversationArtifact` 后，用户仍会用“这个”“刚才那套”“之前那套练胸的”等自然语言引用历史训练内容。如果继续让模型只根据 `conversationSummary` 猜测，会出现找错对象、重复生成或在没有完整 payload 时伪造历史训练的问题。

## 调整思路

新增 `ReferenceResolver`，把引用解析前置到 `/api/chat` 的意图解析之后、内部动作触发之前。解析只使用服务端可验证的 recent artifact summaries 和 `ArtifactIndex` 候选集合，输出 `resolved`、`ambiguous` 或 `not_found`，不把完整 payload 暴露给模型。

## 方案做法

- 近指引用优先读取当前会话 recent artifacts，按 UI/时间顺序解析；多个候选时返回澄清问题。
- 语义引用通过 `searchArtifacts` 在当前用户可访问的 artifact index 中召回候选，并只在候选集合内解析。
- 完整 payload 读取集中到 `getArtifactPayload`，读取前检查 `userId`、`status` 和 payload schema。
- `/api/chat` 对 `ambiguous` 和 `not_found` 直接返回确定性澄清，不再让模型继续承诺修改或生成历史对象。

## 结果

引用解析从模型自由猜测升级为服务端候选受控解析。后续训练解释、重复生成和 Patch 流程可以复用同一个 artifactId 边界，并通过 trace 看到引用解析结果。
