# 2026-06-02 22:19:41 CST Agent 默认无器械候选合同

## 背景

Tool-first Agent 主链已经把动作推荐、routine 和 plan 都收敛到 `searchExercises -> generate*Draft -> validate -> policy -> save` 的结构化工具链。但之前用户没有说明器械时，模型可能不传 `equipment` 或 `homeRequirements`，服务端动作候选就会退化为“任意器械可用”。这会让“今天我想练胸”“今天练胸30分钟”这类请求混入哑铃、弹力带或其他器械动作，也会让长期计划因为缺少器械条件出现不必要追问。

## 原方案问题

只在 prompt 中要求“默认无器械”不够稳定。模型一旦漏传结构化 filters，候选集合和后续 artifact 仍然看不到无器械边界；而把默认写进通用 `exercise-service` 又会污染动作库页面、composer 和普通 `/api/exercises` 查询。

## 调整思路

默认无器械放在 Agent 执行型 `searchExercises` 的输入归一化处，只对 `candidateUse="recommendation" | "routine" | "plan" | "patch"` 生效。服务端只读取结构化输入、`ContextPackage.memorySnapshot.equipment`、`queryUserMemory` / `getUserMemory` 结果和候选 evidence，不读取用户自然语言原文做关键词判断。

## 关键改动

- 执行型 `searchExercises` 在没有正向可用器械、居家条件或已确认可用器械事实时补入 `filters.homeRequirements=["no_equipment"]`。
- `generateRoutineDraft` 和 `generatePlanDraft` 在候选 evidence 或候选动作证明无器械时，把缺省 intent 归一为 `equipment=["自重"]`。
- 长期 plan 的 strategy 会记录 `fieldSources.equipment="default"` 和默认假设，避免把器械缺失当成追问门槛。
- `UserMemorySnapshot` 新增结构化 `equipment` 数组，只承载已确认、非 constraint 的器械记忆。
- 通用动作搜索服务保持原状，不自动默认无器械。

## 验证方式

新增回归测试覆盖动作推荐默认无器械、routine 默认无器械、显式哑铃不被覆盖、长期 plan 缺省器械生成无器械计划、当前无器械条件覆盖历史哑铃记忆，以及通用 `exercise-service` 不受影响。
