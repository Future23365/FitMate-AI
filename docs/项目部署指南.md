# FitMate AI 项目部署指南

本文只记录当前 FitMate AI 仓库的部署方式，不作为通用 Next.js 部署教程。

## 部署形态

当前生产部署由以下部分组成：

```txt
GitHub Actions
  -> Docker Buildx 构建 runner / ops 两个镜像
  -> 推送到 GHCR
  -> 通过 SSH 同步服务器 docker-compose.yml / Caddyfile
  -> 更新服务器 /opt/fitmate/.env 中的 APP_IMAGE / OPS_IMAGE
  -> 执行 Prisma migration
  -> 重建 app 容器
  -> 校验 fitmate-app 运行态镜像

服务器 /opt/fitmate
  -> Caddy 自动 HTTPS 和反向代理
  -> app 运行 Next.js standalone
  -> db 运行 PostgreSQL
  -> ops profile 提供 migrator / seed / refresh_embeddings
```

## 关键文件

- `Dockerfile`：包含 `runner` 和 `ops` 两个 target。`runner` 运行 Next.js standalone 应用；`ops` 保留 Prisma CLI、migration、seed 和 embedding 刷新脚本。
- `.dockerignore`：控制 Docker build 上下文，避免把 `.env`、`.env.local`、`node_modules`、`.next`、测试和调试产物打进镜像。
- `.github/workflows/deploy.yml`：推送到 `main` 分支时构建并部署 app / ops 镜像，也支持 `workflow_dispatch` 手动触发。
- `deploy/server/docker-compose.yml`：服务器 `/opt/fitmate/docker-compose.yml` 模板。
- `deploy/server/Caddyfile`：Caddy HTTPS 和反向代理模板。
- `deploy/server/.env.example`：服务器生产 `.env` 模板；真实 `.env` 只保存在服务器，不提交到 Git。

## 服务器目录

生产部署目录固定为：

```bash
/opt/fitmate
```

首次准备时，将以下文件放到该目录：

```bash
deploy/server/docker-compose.yml
deploy/server/Caddyfile
deploy/server/.env.example
```

然后在服务器上把 `.env.example` 改为 `.env`，填写真实值：

```bash
cd /opt/fitmate
cp .env.example .env
```

之后 GitHub Actions 会自动同步 `docker-compose.yml` 和 `Caddyfile`，但不会覆盖服务器生产 `.env`。

## 服务器环境变量

服务器 `.env` 以 `deploy/server/.env.example` 为模板，当前字段如下：

- `DOMAIN`：Caddy 对外申请 HTTPS 证书和接收请求的域名，不带 `https://`。
- `APP_IMAGE`：Next.js standalone 应用镜像；GitHub Actions 会更新为具体 commit tag。
- `OPS_IMAGE`：运维镜像；GitHub Actions 会更新为具体 commit tag。
- `POSTGRES_DB`：PostgreSQL 初始化数据库名。
- `POSTGRES_USER`：PostgreSQL 用户名。
- `POSTGRES_PASSWORD`：PostgreSQL 密码，必须使用强随机值。
- `DATABASE_URL`：应用和 Prisma CLI 使用的连接串；服务器 Compose 内主机名为 `db`。
- `DEEPSEEK_API_KEY`：生产 `/api/chat` 调用真实模型的必填密钥。
- `DEEPSEEK_API_URL`：可选，覆盖 DeepSeek Chat Completions endpoint。
- `DEEPSEEK_MODEL`：可选，覆盖集中配置中的默认模型。
- `FITMATE_LOCAL_AUTH_SECRET`：本地匿名 auth cookie 生产签名密钥，必须使用强随机值。
- `FITMATE_ADMIN_USER_IDS`：允许访问 `/admin` 的 userId 列表。
- `CONFIRMATION_TOKEN_SECRET`：高影响操作确认 token 签名密钥，必须使用强随机值。
- `EXERCISE_IMAGE_LOCAL_DIR`：app 容器内动作图片读取目录，默认 `exercises_picture`。
- `EXERCISE_IMAGE_PUBLIC_BASE_URL`：前端访问动作图片的基础 URL，默认 `/api/exercise-images`。
- `ENABLE_AI_TRACE_LOG`：生产环境是否写入 AI trace；公开环境建议保持 `false`。

## GitHub Actions 配置

当前 workflow 文件是 `.github/workflows/deploy.yml`。

触发条件：

- `workflow_dispatch`：手动触发。
- push 到 `main`：自动构建和部署。
- 如果本次 push 的全部变更都属于 `.agents/**`、`.codex/**`、`docs/**`、`tests/**`、`manual-tests/**`、`example/**`、`README.md` 等非运行态路径，则跳过自动部署。

需要配置的 GitHub Repository secrets：

- `SERVER_HOST`
- `SERVER_PORT`
- `SERVER_USER`
- `SERVER_SSH_KEY`

workflow 会使用 GitHub Actions 注入的 `GITHUB_TOKEN` 登录 GHCR 并推送镜像。

## 部署流程

workflow 当前会执行这些步骤：

1. 拉取仓库代码。
2. 准备小写 GHCR 镜像名。
3. 安装 Docker Buildx。
4. 构建并推送 `runner` 镜像：

```txt
ghcr.io/<owner>/<repo>:latest
ghcr.io/<owner>/<repo>:<commit-sha>
```

5. 构建并推送 `ops` 镜像：

```txt
ghcr.io/<owner>/<repo>-ops:latest
ghcr.io/<owner>/<repo>-ops:<commit-sha>
```

6. 通过 SSH 同步 `deploy/server/docker-compose.yml` 和 `deploy/server/Caddyfile` 到 `/opt/fitmate`。
7. 更新服务器 `.env` 中的 `APP_IMAGE` 和 `OPS_IMAGE`。
8. 使用 `docker compose --profile ops config --images` 校验 app / ops 镜像都被最终 Compose 配置消费。
9. 拉取新镜像。
10. 用 `migrator` 服务执行：

```bash
npx prisma migrate deploy
```

11. 重建 `fitmate-app` 容器。
12. 确保 `caddy` 和 `db` 运行。
13. 用 `docker inspect fitmate-app` 校验运行态镜像等于当前 commit 镜像。
14. 清理无引用旧镜像。

## 首次上线

首次上线时，先完成服务器 `.env`，再手动触发一次 GitHub Actions 部署。

部署成功后，在服务器上执行 seed 和 embedding 刷新：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml --profile ops run --rm seed
docker compose --env-file .env -f docker-compose.yml --profile ops run --rm refresh_embeddings
```

如果动作 seed 数据后续发生变化，也需要再次执行这两个命令。

## 生产迁移

生产环境不要使用：

```bash
npm run db:migrate
```

该脚本执行的是 `prisma migrate dev`，只适合本地开发。

生产部署时，GitHub Actions 会通过 `migrator` 服务自动执行：

```bash
npx prisma migrate deploy
```

如果需要在服务器上手动执行 migration：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml --profile ops run --rm migrator
```

## 常用运维命令

查看容器状态：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml ps
```

查看 app 日志：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml logs -f app
```

查看 Caddy 日志：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml logs -f caddy
```

服务器手动修改 `.env` 后，重建 app 容器使配置生效：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml up -d --force-recreate app
```

检查当前 `.env` 中的目标镜像：

```bash
cd /opt/fitmate
grep '^APP_IMAGE=' .env
grep '^OPS_IMAGE=' .env
```

检查运行中的 app 容器镜像：

```bash
docker inspect fitmate-app --format '{{.Config.Image}}'
```

检查 Compose 最终会使用的镜像：

```bash
cd /opt/fitmate
docker compose --env-file .env -f docker-compose.yml --profile ops config --images
```

清理无引用旧镜像：

```bash
docker image prune -f
```

## 注意事项

- 服务器 PostgreSQL 只绑定宿主机 `127.0.0.1:5432`，不对公网开放；本地 DBeaver、Prisma 或 `psql` 需要通过 SSH tunnel 连接。
- 生产环境必须显式配置稳定的 `FITMATE_LOCAL_AUTH_SECRET` 和 `CONFIRMATION_TOKEN_SECRET`。
- 生产 Agent 当前只开放只读查询与可见训练方案输出，不会由模型直接保存或覆盖训练计划。
- `exercises_picture/` 默认会从镜像初始化到 Docker volume；如果迁移到 CDN 或对象存储，需要同步调整 `EXERCISE_IMAGE_PUBLIC_BASE_URL`。
